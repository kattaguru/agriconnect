1. Introduction
1.1 Purpose
This document describes how AgriConnect is designed and built. It is the reference for developers, examiners and future contributors: it explains the architecture, the database, every API endpoint, the core algorithms, the security model and the plan for the AI components.
1.2 Scope
AgriConnect is a cloud-based platform with two primary user groups, farmers and agricultural workers. Phase 1 is a job marketplace. Later phases add a farmer profit simulator, crop intelligence, crop-disease detection, retrieval-augmented generation (RAG), a tool-using AI agent and market intelligence. This TDD covers both what exists today and what is designed for later, and marks each clearly.

2. System Overview
2.1 Problem and goals
Farmers struggle to find reliable workers at the right time, and workers struggle to find nearby farm work with clear wages and dates. AgriConnect connects the two sides, builds a portable reputation for workers, and later adds evidence-grounded decision support for farmers.
2.2 Design principles
•	Marketplace first. The labour marketplace must work end to end before any AI feature is added.
•	Simple before clever. A transparent rule-based matcher is the baseline; ML must beat it to earn a place.
•	Grounded AI. RAG answers cite sources; the agent only calls controlled tools; consequential actions need human confirmation.
•	Modular monolith. One deployable application with clean module boundaries; extract services only when a real need appears.
•	Security and testing from day one. Authorisation is enforced server-side on every protected route and is covered by tests.
•	Honest uncertainty. Predictions, forecasts and simulations are decision support, never guarantees.
2.3 Constraints and assumptions
•	Single developer, one academic year; scope must stay demonstrable and testable.
•	Cloud budget limited to student credits; expensive services stay off when idle.
•	Users may have low bandwidth and low digital literacy; mobile-first, lightweight screens.
•	Coordinates are supplied by the client (GPS or manual); no paid map service is required for the MVP.
•	Training data for disease detection comes from public datasets; real labour-matching data does not exist yet.
2.4 Key design decision: Python / FastAPI backend
The original blueprint proposed Java 21 with Spring Boot. During implementation the backend was changed to Python 3.12 with FastAPI. The reasons: the ML, RAG and agent components are Python-native, so one language avoids a second service and glue code; FastAPI provides validation and OpenAPI docs automatically; and the code could be built and tested in the available environment. The architecture (modular monolith, REST, JWT, PostgreSQL, Docker, Azure) is unchanged. See the decision log in the Project Master Document.
3. Architecture
3.1 Architectural style
A modular monolith exposing a REST/JSON API. Modules share one database and one deployable, but each has its own router, and business rules are kept out of route handlers where they grow complex. ML and RAG capabilities are added as internal modules first and may later be split into a separate Python service if scaling or dependency weight demands it.

4.2 Request lifecycle
1.	The request passes through CORS middleware.
2.	FastAPI validates the path, query and JSON body against Pydantic schemas (invalid input returns 422).
3.	current_user reads the Authorization: Bearer header, verifies the JWT and loads the user (missing or bad token returns 401).
4.	require_role(...) checks the user role (wrong role returns 403).
5.	The route handler checks ownership rules (for example, only the farm owner may view applications), performs the change and commits the transaction.
6.	The result is mapped to an output schema and returned as JSON.
4.3 Error handling
HTTP code	Meaning	Examples
200 / 201	Success / created	Apply, accept, complete; register, create farm, job, review
401	Not authenticated	No token, invalid or expired token, wrong password
403	Authenticated but not allowed	Worker posts a job; farmer opens another farmer's job; stranger reviews a booking
404	Resource missing	Unknown job, farm, application, booking, worker
409	State conflict	Duplicate email, duplicate application, job no longer open, review before completion, double review
422	Validation failed	Weak password, invalid role, past start date, rating outside 1-5, bad coordinates

4.4 Transactions and consistency
Each request uses one database session. Multi-step changes commit together: accepting an application updates the application, creates the booking, and (when the job is full) changes the job status and rejects remaining pending applications in one transaction. Uniqueness is also enforced by database constraints (one application per worker per job, one review per reviewer per booking, unique email) so that races cannot create duplicates.

7. Domain Logic and Algorithms
7.1 State machines
Entity	States and transitions
Job	OPEN -> FILLED (when accepted bookings >= workers_required) -> COMPLETED (when the last confirmed booking is completed). CANCELLED is reserved for a future cancel feature.
Application	PENDING -> ACCEPTED (farmer accepts) or REJECTED (job filled by others). Terminal states cannot change.
Booking	CONFIRMED -> COMPLETED (farmer confirms the work is done).

7.2 Accepting an application
1.	Load the application and its job; verify the caller owns the job's farm (else 403).
2.	Require application status PENDING and job status OPEN (else 409).
3.	Set application to ACCEPTED and create a CONFIRMED booking for that worker.
4.	Count bookings for the job. If the count reaches workers_required, set the job to FILLED and set all remaining PENDING applications to REJECTED.
5.	Commit once; return the booking.
7.3 Completing work and reviews
Only the owning farmer can complete a booking. When the job is FILLED and no CONFIRMED bookings remain, the job becomes COMPLETED. A review is allowed only after the booking is COMPLETED, only for the farmer or the assigned worker, and the reviewed party is always the other participant. A user can review a booking once.
7.4 Rule-based matching engine
The matcher ranks every worker profile for a job using a transparent weighted score in the range 0 to 1:
score = 0.40 * distance_score
      + 0.20 * availability      (1 if available else 0)
      + 0.20 * skill_match       (1 if job needs no skill, or the worker lists it)
      + 0.10 * experience_score  (min(years, 10) / 10)
      + 0.10 * reputation_score  (avg_rating / 5; 0.5 if unrated)
 
distance_score = max(0, 1 - distance_km / 50)    (0 if the worker has no location)
Worked example. A worker 3 km away, available, with the required skill, 5 years experience and no ratings scores 0.4 x 0.94 + 0.2 + 0.2 + 0.1 x 0.5 + 0.1 x 0.5 = 0.876. A worker 186 km away, lacking the skill, with 1 year experience and no ratings scores 0.2 + 0.01 + 0.05 = 0.26.
•	Explainability. Every result lists human-readable reasons, so farmers understand why a worker is ranked high.
•	Complexity. O(W) over W worker profiles per request, plus one rating query per worker. Fine for a prototype; see Section 14.
•	Weights are constants in app/matching.py and are documented so they can be tuned and evaluated.
•	Evolution. Once real matching outcomes exist (accepted, completed, no-show), train a ranking model and compare it against this baseline on top-k relevance and completion rate. This comparison is the proposed research contribution.
7.5 Nearby-job search
Open jobs are loaded, the Haversine great-circle distance from the worker's coordinates to each farm is computed, jobs beyond radius_km are dropped, an optional skill filter is applied, and results are sorted by distance. Distance is rounded to 0.1 km.
8. Security Design
8.1 Authentication
•	Passwords are hashed with bcrypt (salted, slow). Passwords must be 8 to 64 characters.
•	Login returns a JWT (HS256) containing the user id (sub), role and expiry (12 hours by default). The secret comes from the JWT_SECRET environment variable.
•	Every protected request re-loads the user from the database, so a deleted user's token stops working.
•	Only FARMER and WORKER may self-register; ADMIN and AGRI_EXPERT accounts must be created by an administrator (planned).

9. AI / ML Components and Profit Simulator (Planned)
Status: This section is a design, not an implementation. No model has been trained yet, and no accuracy figures are claimed.
9.1 Crop intelligence
Inputs: location, land size, soil values (pH, N, P, K) when available, water availability, season, budget, crop history. Outputs: candidate crops, water need, approximate duration, input considerations, the factors behind the result, and stated uncertainty. Approach: start with a rule/knowledge-based scorer over a curated crop table; optionally compare with a small scikit-learn classifier trained on a public crop-recommendation dataset. Results are shown as decision support with a pointer to local agricultural officers.
9.2 Crop-disease detection
Farmer uploads image -> API validates type/size -> store in blob storage -> ML module
  -> preprocess (resize, normalise) -> CNN classifier (transfer learning)
  -> label + confidence -> if confidence < threshold: "not sure, consult an expert"
  -> RAG retrieves guidance for the label -> plain-language explanation with sources
•	Model: transfer learning from an ImageNet-pretrained network (for example MobileNetV3 or EfficientNet-B0) fine-tuned on a public plant-disease dataset.
•	Evaluation: accuracy, per-class precision/recall/F1, confusion matrix, and performance on real field photos taken outside the training distribution. Lab-style datasets often overstate real-world accuracy, so reporting this gap is a core result.
•	Safety: low-confidence predictions are not presented as findings; output always states it is not a professional diagnosis.
9.3 Agricultural RAG
1.	Collect trusted documents (extension bulletins, government agriculture material) and record source metadata.
2.	Extract text, clean, and split into overlapping chunks (about 500 tokens, 50 overlap).
3.	Embed chunks and store vectors in PostgreSQL with pgvector.
4.	At question time embed the query, retrieve the top-k chunks, and pass them to the LLM with an instruction to answer only from the context and to say when the context is insufficient.
5.	Return the answer with source references (document, page).
Evaluation: a hand-built set of 30 to 50 realistic farmer questions; measure retrieval relevance (is the right chunk in the top k?), groundedness (is every claim supported by retrieved text?) and citation coverage.
9.4 Farm AI agent
The agent is an orchestrator that can call only whitelisted application tools, each running with the calling user's permissions:
Tool	Effect	Confirmation
getFarmDetails	Read the user's farm data	No
findWorkers	Run the matcher for a job	No
searchAgriDocs	RAG lookup	No
getMarketInfo	Read prices	No
analyzeCropImage	Run disease model on an uploaded image	No
runProfitSimulation	Run the profit simulator with the user's inputs	No
createJobDraft	Prepare a job (not posted)	User reviews
accept worker, post job, payments	Consequential actions	Always explicit user confirmation

Metrics: task success rate, tool-call accuracy, confirmation rate, latency and cost per interaction. The agent is never given unrestricted database or shell access.
9.5 Market intelligence
Ingest legitimate public price data, normalise crop, market, unit and date, store with source and date, show current and historical trends, and compare net return (price minus estimated transport cost) across nearby markets. A simple time-series forecast (for example seasonal-naive versus ARIMA/Prophet) may be explored later and must be shown with uncertainty; the product never promises a future price.
9.6 ML-based matching
Collect outcomes (accepted, completed, cancelled, no-show, rating) and features (distance, skill match, experience, reputation, past completion). Train a gradient-boosted ranking model and compare it with the rule-based baseline using top-k relevance and completion rate. Keep whichever performs better and remains explainable.
9.7 Farmer profit simulator
A deterministic what-if calculator that helps a farmer see whether a crop is likely to pay and where to sell it. It uses transparent arithmetic over inputs the farmer can edit, so it needs no training data and can be fully unit-tested. It also connects the marketplace to farm economics: the labour cost line can be pre-filled from real wages posted on AgriConnect.
gross_revenue    = expected_yield_qtl * selling_price_per_qtl
labour_cost      = workers * days * wage_per_day      (default from average posted wages)
total_cost       = seed + fertilizer + pesticide + irrigation + labour + machinery + transport + other
net_profit       = gross_revenue - total_cost
profit_per_acre  = net_profit / area_acres
break_even_price = total_cost / expected_yield_qtl
break_even_yield = total_cost / selling_price_per_qtl
 
Selling option net price (per quintal) =
    ( market_price - transport_per_qtl - commission - storage_cost_per_day * days_stored )
    * ( 1 - shrinkage_percent / 100 )
•	Scenarios: low / base / high cases for yield and price (for example -20%, 0, +20%), shown side by side so the farmer sees the risk range, not a single number.
•	Compare selling options: local market now, a farther market with a higher price but more transport, or storing for some days. Options are ranked by net price and net profit.
•	Sensitivity: show how profit changes for +/-10% price and yield, and highlight the break-even price.
•	Interface (planned): POST /api/simulations/profit takes the inputs above and returns the scenarios, break-even values and ranked selling options. Saved simulations are stored per farm for later comparison.
•	Honesty: results depend on the numbers entered; the screen states that prices and yields are estimates, not guarantees.
•	Tests: unit tests for each formula with hand-calculated cases, plus edge cases for zero yield and zero price.

14. Performance and Scalability
Concern	Current behaviour	Planned improvement
Nearby jobs	Loads all open jobs and computes distance in Python	Bounding-box pre-filter on lat/lon columns with an index; later PostGIS geospatial index
Matching	Loops over all workers with one rating query each	Pre-filter by distance box and availability; compute ratings in a single grouped query; cache
Lists	Return full lists	Add pagination (limit/offset or cursor)
Repeated reads	No cache	Redis for hot reads (open jobs, worker reputation)
Long tasks (ML, embeddings)	Not present	Background worker queue so the API stays responsive
Scaling out	Single instance	Stateless API (JWT) allows multiple replicas behind a load balancer

Expected prototype load is tens of concurrent users, which the current design handles comfortably; the improvements above are for growth beyond a pilot.
15. Known Limitations and Technical Debt
#	Limitation	Impact	Planned fix
1	No database migrations (create_all)	Schema changes can lose data	Adopt Alembic
2	No token refresh or revocation	A stolen token is valid until expiry	Short-lived access + refresh tokens
3	No rate limiting	Brute force and abuse	Middleware or gateway limits
4	No double-booking check	A worker can be booked on overlapping dates	Check date overlap when accepting
5	CANCELLED status unused	No way to cancel a job or booking	Add cancel endpoints and no-show tracking
6	Skills stored as a JSON list	No skill catalogue or levels	Normalise into skills tables
7	Distance is straight-line	Road distance can differ	Optional routing API later
8	No notifications	Workers must open the app to see jobs	In-app, then WhatsApp/SMS
9	No admin or verification	No moderation or trust badges	Admin module, phone OTP
10	Wages and money as floats	Rounding in future payments	Use decimal/integer paise before payments
