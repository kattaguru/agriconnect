1. Introduction
1.1 Purpose
This Software Requirements Specification (SRS) states what AgriConnect must do and the qualities it must have. Part B (the Development Specification) states how the work will be carried out: process, standards, testing, release and schedule. Together they let any developer or examiner understand the scope without reading the code.
1.2 Product scope
AgriConnect is a web platform that (1) connects farmers who need agricultural labour with workers looking for nearby work, builds trusted ratings, and (2) gives farmers decision support: a profit simulator, crop guidance, crop-disease detection, a question-answering assistant grounded in trusted documents, and market price information.
1.3 Definitions
Term	Meaning
Farmer	A user who owns or manages farmland and posts jobs
Worker	A user who offers agricultural labour
Job	A posted piece of farm work with date, duration, wage and number of workers needed
Application	A worker's request to take a job
Booking	A confirmed assignment created when a farmer accepts an application
Match score	A 0 to 1 ranking of how suitable a worker is for a job
RAG	Retrieval-augmented generation: answers built from retrieved trusted documents
Quintal	100 kg

2. Overall Description
2.1 Product perspective
AgriConnect is a new, self-contained system: a web front end, a REST API, a relational database, and later ML/RAG components and cloud storage. It does not replace government systems and does not process payments in the first release.
2.2 User classes
User class	Description	Needs
Farmer	Small or medium farmer; may have limited digital literacy; mostly on a smartphone	Find reliable workers quickly, see why a worker is suggested, understand costs and profit, get crop and disease help
Worker	Agricultural labourer or skilled worker; low bandwidth; may prefer voice and local language	Find nearby jobs, see wage and dates clearly, build a reputation
Agri expert (planned)	Agronomist or extension officer	Review AI answers, add trusted guidance
Administrator (planned)	Platform operator	Moderate users, view metrics, manage knowledge base

2.3 Operating environment
•	Server: Linux container running Python 3.12, FastAPI, PostgreSQL 16 (SQLite for development).
•	Client: modern mobile and desktop browsers; installable PWA planned.
•	Network: must remain usable on slow or intermittent connections.
2.4 Constraints
•	One developer and one academic year; features are prioritised with MoSCoW.
•	Limited cloud budget (student credits).
•	No real labour-matching data at launch; AI features rely on public datasets and curated documents.
•	No payment processing, no fully autonomous agent actions, and no claims of guaranteed yield, price or diagnosis.
2.5 Assumptions and dependencies
•	Users have a phone number and either GPS or can enter a location.
•	Public datasets (plant disease, market prices) remain available under usable licences.
•	An LLM and embedding provider is available for RAG within budget.
•	Pilot users can be reached for interviews and testing.

4. Use Cases
UC-01 Register and set up a worker profile
Field	Description
Actor	Worker
Precondition	None
Main flow	1. Worker registers with role WORKER. 2. System creates the account and an empty profile and returns a token. 3. Worker sets skills, experience, location and availability. 4. System saves the profile.
Alternate flows	Email already used: 409. Password too short or invalid role: 422.
Postcondition	Worker appears in matching results for jobs.

UC-02 Post a job
Field	Description
Actor	Farmer
Precondition	Logged in as FARMER; at least one farm exists
Main flow	1. Farmer creates a farm (once). 2. Farmer enters work type, skill, workers needed, start date, duration and wage. 3. System validates and saves the job as OPEN.
Alternate flows	Farm belongs to another farmer: 403. Start date in the past or wage not positive: 422.
Postcondition	Job is visible in open and nearby searches.

UC-03 Find nearby work and apply
Field	Description
Actor	Worker
Precondition	Logged in as WORKER
Main flow	1. Worker searches nearby jobs with location, radius and optional skill. 2. System returns open jobs nearest first with distance. 3. Worker opens a job and applies. 4. System records a PENDING application.
Alternate flows	Already applied: 409. Job no longer open: 409.
Postcondition	Farmer can see the application.

UC-04 Review candidates and hire
Field	Description
Actor	Farmer
Precondition	Job owned by the farmer has applications
Main flow	1. Farmer opens ranked matches with scores and reasons. 2. Farmer opens applications. 3. Farmer accepts an applicant. 4. System creates a CONFIRMED booking. 5. If enough workers are accepted, the job becomes FILLED and other pending applications are rejected.
Alternate flows	Not the owner: 403. Application not pending or job not open: 409.
Postcondition	Worker sees the booking in their list.

UC-05 Complete work and rate
Field	Description
Actor	Farmer, Worker
Precondition	Confirmed booking exists
Main flow	1. Farmer marks the booking complete. 2. When no confirmed bookings remain, the job becomes COMPLETED. 3. Farmer and worker each submit a rating. 4. System updates the worker's average rating.
Alternate flows	Review before completion: 409. Third party reviewing: 403. Second review by same person: 409.
Postcondition	Reputation is updated and used in future matching.

UC-06 Simulate crop profit (planned)
Field	Description
Actor	Farmer
Precondition	Logged in as FARMER
Main flow	1. Farmer selects a crop and enters area, yield, price and costs (labour pre-filled from posted wages if available). 2. System shows revenue, cost, profit, break-even and low/base/high scenarios. 3. Farmer adds selling options and compares net price. 4. Farmer saves the simulation.
Alternate flows	Missing or zero yield or price: show validation message instead of a result.
Postcondition	Simulation saved for comparison.

UC-07 Check a diseased crop (planned)
Field	Description
Actor	Farmer
Precondition	Logged in as FARMER
Main flow	1. Farmer uploads a leaf photo. 2. System validates and classifies the image. 3. System returns label and confidence with sourced guidance and a disclaimer.
Alternate flows	Low confidence: system says it is not sure and suggests an expert. Invalid or oversized file: rejected.
Postcondition	Image and result saved to the farm history.

6. Non-Functional Requirements
ID	Category	Requirement
NFR-PERF-01	Performance	Typical API calls respond within 500 ms at the 95th percentile for up to 50 concurrent users on the prototype deployment
NFR-PERF-02	Performance	Nearby-job and matching queries stay under 1 s for up to 10,000 open jobs and 10,000 workers after the planned index and pagination work
NFR-SEC-01	Security	Passwords hashed with bcrypt; JWT secret from environment; no secrets in the repository
NFR-SEC-02	Security	All authorisation is enforced on the server; ownership and role checks are covered by automated tests

NFR-POR-01	Portability	The application runs from a Docker image on any container host
NFR-AI-01	AI safety	AI outputs are decision support; low-confidence or unsupported answers are labelled; no autonomous consequential actions

9. Development Process
9.1 Approach
Iterative delivery in two-week sprints. Each sprint ends with a working, tested increment that is demonstrated. Work is tracked on a simple board (To do, In progress, In review, Done) in GitHub Projects.
9.2 Version control
•	GitHub repository with a protected main branch that is always deployable.
•	Branches named feature/<short-name>, fix/<short-name>; short-lived; merged by pull request.
•	Commit messages in the form type: summary (feat, fix, test, docs, refactor, chore).
•	Every pull request has a description, passing tests, and is self-reviewed against the Definition of Done before merge.
•	Semantic versions tagged at each milestone (0.1.0 backend MVP, 0.2.0 frontend MVP, and so on).
9.3 Change control
Requirements changes are recorded in the change log of the Project Master Document, with the reason and the effect on schedule. Scope additions require an equal-size removal or an explicit schedule change.
10. Coding and Documentation Standards
Area	Standard
Python style	PEP 8; type hints on public functions; format with Black and lint with Ruff (to be added in CI)
Structure	Routers handle HTTP only; logic that grows complex moves to a service module (as matching.py does)
Naming	snake_case for Python and JSON; plural table names; enum values in upper case
Validation	All request data goes through Pydantic schemas; never build SQL from strings
Errors	Raise HTTPException with the correct status code and a clear detail message
Secrets	Environment variables only; never commit secrets; .env in .gitignore
Comments	Explain why, not what; document formulas and non-obvious rules (for example matching weights)
Frontend	TypeScript strict mode; small components; API client generated from OpenAPI
Docs	README kept current; architecture decisions recorded in the decision log

Unit	Pure functions: matching score, geo distance, profit formulas	pytest	Hand-calculated expected values; edge cases

Frontend	Components and journeys	Vitest, Playwright	Critical journeys: register, post job, apply, accept

Usability	Real users	Observation and interviews	Task completion with 5 or more pilot users

15. Definition of Ready and Done
Definition of Ready (a task can start when)
•	It traces to a requirement ID.
•	Acceptance criteria are written.
•	Dependencies are available (data, accounts, design).
Definition of Done (a task is finished when)
•	Code is merged to main through a pull request.
•	Unit and API tests are written and passing; role and validation cases included.
•	No secrets in code; inputs validated; errors return correct status codes.
•	The API change appears correctly in Swagger UI and the docs are updated.
•	The feature was exercised manually once end to end.
•	For AI work: evaluation set, metrics and limitations recorded.
